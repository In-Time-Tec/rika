# Durable Execution mapping

Every Turn maps deterministically to one top-level Baton Execution, and every Thread maps to one stable Baton Session. Baton owns execution events, waits, children, cancellation, replay, and terminal state; Rika stores the product records and disposable read projections that refer to them.

Baton `runId` and `childRunId` values are opaque execution IDs. Rika does not add namespace prefixes or recover parentage from their text. Baton persists each child invocation correlation in `ChildLinked`; projected child events carry the returned child Run ID and invocation ID, and every later inspect, replay, follow, cancel, or approval operation addresses that Run ID directly.

The Turn's resolved route and Workspace are supplied to exact root admission. Rika constructs one pinned executable and a complete immutable, secret-free registration set for that Turn, then calls Baton `Runtime.start` with the route's pinned recursive tree policy; duplicate admission returns the same opaque Run link, while changed admission under the same Turn fails. Baton persists the manifest, registration catalog, root depth, and tree policy atomically, so an admitted Execution restarts without reading Product rows, startup route maps, current configuration, the current directory, or fallback routes. Registration payloads contain provider connection and credential references, never resolved credential values; Rika's resolver dereferences those references through application credential services when reconstructing scoped execution resources.

At Turn admission, Baton persists the executable manifest and every required registration. The registration codecs are `rika-application-context`, `rika-model-route`, `rika-model-registry-route`, `rika-compaction`, `rika-kernel-profile`, `rika-skill`, `@batonfx/harness/snapshot`, and `rika-tool`. They contain the application context with the Workspace and resolved execution route; a model-route and model-registry route for Root, Title, Compaction, Oracle, Librarian, Painter, ReadThread, Review, Surgeon, and Task; the compaction policy; the admitted kernel profile; each pinned skill's name and digest, never its body; the continual-harness snapshot pinned under the `rika-harness-snapshot` capability; and the static `typescript` tool contract. Baton's Execution Host supplies `run_child` and `run_child_group` dynamically when the persisted depth and direct-child quota permit them. Model-route registrations retain credential references, such as the credential identity and environment-variable name. They never retain resolved credential values, API keys, tokens, authorization values, or passwords.

On restart, Baton resolves the persisted active executable and registrations. Rika reconstructs the same executable from the persisted application context and verifies that every required registration is present and unchanged. It rejects extra, missing, changed, or non-admitted registrations.

Rika accesses Baton execution through the `ExecutionGateway`: `startTurn`, `cancelTurn`, `steerTurn`, `approveTurn`, `denyTurn`, `watchTurn`, and `inspectTurn`. `startTurn` admits durable work and returns its opaque execution link. `cancelTurn` sends cancellation to Baton. `steerTurn` adds durable steering text with an idempotency key. `watchTurn` streams projected Run events from an optional cursor. Rika commits each streamed projection before delivering it once through the live callback; completion returns the latest durable state, units, and checkpoint without retaining or replaying historical changes. A recovery watch with no new events reads that result from the stored projection. `inspectTurn` reports the current status and cursor, or `unavailable` when Baton no longer has the Run.

Every active execution observer also delivers Baton's memory-only model previews. Reasoning and answer deltas are accumulated in memory by Baton at a bounded cadence and forwarded to connected interactive clients as disposable `ExecutionModelPreviewed` frames; they are never written to `rika.db` or `baton.db`, never advance a projector checkpoint, and disappear on disconnect or resync. The durable committed response is the only model output Rika persists.

Rika treats the Baton and Effect versions pinned in the root package catalog as one runtime compatibility unit. They are installed and upgraded together so durable values never cross between different Effect runtime identities.
