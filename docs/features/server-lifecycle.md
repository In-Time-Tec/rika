# Server process lifecycle

The server moves through `starting`, `ready`, `grace`, `draining`, and `stopped`. After the last client disconnects the server lingers in `grace` (fifteen minutes by default, `RIKA_INTERNAL_SERVER_GRACE` overrides) so quick relaunches reattach warm instead of paying a cold spawn and product build. An authenticated client may cancel the grace period; clients arriving during draining are rejected, and startup detects different builds, foreign listeners, unsafe tokens, and failed ownership rather than opening another state owner. A newly launched different build closes admission, drains accepted transient mutations, shuts down the old owner, waits for its listener and SQLite resources to be released, and starts as the sole owner. Durable running Executions survive that ownership transfer. Existing interactive clients remain open, retry while the owner changes, then resync from the replacement without initiating another replacement.

Quitting Rika cancels the work it was running. A quitting interactive client asks the server to stop every non-terminal turn before the client process exits, so the durable stop intent survives an interrupted shutdown; the server only honours that request when no other client is attached. A client that dies without warning cannot ask, so the server treats the loopback connection as the liveness signal: once the last client detaches it waits `RIKA_INTERNAL_SERVER_ABANDON` (five seconds by default, never longer than the grace period) and, if no client has reattached and the server is not draining for a replacement, records the stop intent and settles every non-terminal turn as cancelled. Reattaching inside that window cancels nothing, a server that is being superseded never cancels, and settlement is idempotent because a stop intent that is not settled is settled by the next server that starts.

The loopback listener stays owned until Baton and product SQLite close. The old server requests its own shutdown after acknowledging takeover, while the launching client also waits for process and listener release before spawning; a lost takeover connection cannot strand a permanently draining server. Graceful shutdown bounds each client close and the server scope so signals can finish promptly. After an abrupt stop, the operating system releases the listener and the next server relies on durable reconciliation rather than process memory.
