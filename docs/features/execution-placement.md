# Runner and Orb execution

Creating a Thread without an explicit target selects the current Runner. Selecting Orb creates an `orb` Thread backed by E2B. The target is durable and immutable; it is not encoded in Thread identity. Thread and executor-assignment IDs are independently generated opaque identifiers, and an assignment refers to its Thread explicitly. An unavailable Executor leaves the hosted Thread durable and visibly waiting instead of cancelling it or silently moving it.

The selected Executor owns Workspace access, native tool effects, and processes. The API hosts Generalist's PostgreSQL Runtime, model loop, and encrypted provider credential use, then dispatches Workspace operations through Generalist's stable operation key. Hosted contracts carry opaque Workspace Identity rather than a host-local path. The Executor alone maps that identity to a path and accepts work only while holding the current assignment generation and lease epoch.

A Runner is a registered user-controlled process rooted in one approved checkout. Interactive Rika registers the current checkout; headless Rika can accept remotely created Threads. Runner registration, fresh connection, and reconnect all carry the current Runner protocol revision. The API rejects a missing or obsolete revision before admitting the process to a session, so an old installed Runner cannot accept current tool work and fail later with an ambiguous host timeout. This Runner-only gate does not change the Orb access protocol. A Runner never becomes an Orb implicitly.

A registered Runner is admitted to a Runner Thread only while that Thread has demand: a pending assignment, a live viewing client, an active or queued Turn, or queued protocol work. Idle historical Threads of the same checkout do not each hold an open Runner session, so a checkout with many past Threads costs one registration poll rather than one socket and heartbeat per Thread. While a Runner is still connecting, Generalist retries transient Executor unavailability for the same durable operation key for about thirty seconds before the tool call fails; a missing Executor or checkout is a placement failure and is not retried.

An Orb created by a local Rika client starts from an immutable snapshot of the selected local Workspace. A Project-backed Orb first clones the selected repository and then overlays that snapshot without replacing `.git`; a projectless Orb restores it into a blank Workspace. The snapshot carries tracked changes and untracked nonignored files, preserves local deletions, and excludes Git internals, ignored files, local agent state, dependency and build output, credential files, and detected secret material. Rika encrypts the uploaded archive, claims it atomically with Thread creation, verifies that a Project seed names the selected GitHub repository, and restores it before repository setup. Browser-created Orbs have no local snapshot and retain clone-or-blank behavior.

Orb preparation runs `.agents/setup` once per checkout and `.agents/resume` once per wake. A hook that exits unsuccessfully does not fail preparation: the host records the hook outcome as `failed` evidence, keeps its output in the preparation log, and the Workspace stays usable, as in an Amp orb whose setup failed. Preparation itself can still fail (checkout, capabilities, credentials); the API waits for the provisioned generation to report `ready`, retries a retryable preparation failure up to three times, and otherwise fails the Run with the preparation phase and message. The Orb host probes Workspace visibility as the Workspace user, not as the host process user.

When the API admits an Orb prompt, it reports readiness from the durable assignment, lease, preparation, and checkpoint state before waking the command worker. A Workspace with no prior successful preparation or checkpoint is `fresh`, so the TUI shows `Preparing sandbox` until prompt admission and then `Waiting`. A prepared Workspace with an active lease is `hot`, so later prompts go directly to `Waiting`. A previously prepared Workspace whose lease is no longer live, or whose replacement generation is restoring prior state, is `cold`, so the TUI shows `Waking sandbox` until prompt admission. These statuses come from Workspace lifecycle state, never from prompt count or a stale client connection state; model output changes `Waiting` to `Streaming` through the normal execution events.

An Orb pauses without memory after fifteen idle minutes and cold-resumes when authorized work or a portal request arrives. Recovery uses committed Generalist and API cursors, checkout identity, and verified Workspace checkpoint artifacts; a verified checkpoint supersedes the creation snapshot. Portals expose an authenticated E2B service hostname through the shared Thread protocol. E2B credentials never reach a CLI, TUI, or browser.

The shared Thread protocol also owns repository service start/stop and portal requests. `rika thread service`, `rika thread portal`, and the FoldKit client call that protocol; they do not contact E2B directly. `rika thread sync` submits one approved commit SHA to the API repository-publication workflow with a stable idempotency key. The API authorizes the Thread's Project and repository, then performs the bounded branch publication; a client never receives the installation credential.
