# Client behaviour verified below what a user sees

**Gain:** the interactive client is covered at two levels that are cheap and fast. Unit tests drive the real controller and assert the model it produces, and the in-process TUI suite drives the real Surface on a test renderer and asserts rendered frames without paying for a spawned server, a PTY, or a kernel worker. Both run in the default gate, so a change to projection or reduction is caught in seconds.

**Cost:** neither level watches the seam where the client actually assembles itself. A controller test asserts the value a function returned, one layer below the line a reader looks at, and the in-process suite asserts frames but has no lane that waits for the activity line while a cell is running — so a turn can render its work and still report nothing in progress with every gate green. Three defects have lived in that gap: a kernel pool released by the first cell that built it, an activity summary computed by a reducer no live turn reaches, and an activity line that a real client computes correctly and the process suite cannot observe. Each was found by a process test failing for a reason no faster gate could name, and each was invisible to the level directly beneath it.

**Rejected:** raising process coverage to carry ordinary client behaviour makes the slowest, least deterministic gate the one that decides whether a change is correct, and its failures name a captured frame rather than a value. Trusting the controller level alone is what allowed all three: a function returning the right value proves nothing about whether its caller is on the path a user's client takes. Closing it means an in-process interactive lane that waits for the rendered activity line on a cell turn, so the assertion sits where the reader's attention does.
